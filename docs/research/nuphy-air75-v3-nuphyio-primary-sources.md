# NuPhyIO primary-source check for Air75 V3 over 2.4 GHz

Date: 2026-07-16

## Scope and safety boundary

This supplements `nuphy-air75-v3-battery.md`. The initial check inspected live
Linux USB/HID metadata and the JavaScript delivered by NuPhy's official sites.
A later, explicitly approved experiment granted temporary per-user ACLs to
only the 64-byte raw-HID interface, authorized official NuPhyIO in an isolated
browser profile, and captured commands generated by NuPhyIO itself. It did not
replay a command outside NuPhyIO, create a udev rule, install software, update
firmware, change keyboard settings, use Bluetooth, or modify Waybar.

## Official delivery and device support

- NuPhy's firmware page routes Air75 V3 to NuPhyIO rather than to the QMK
  firmware path used by Air75 V2: [NuPhy firmware page](https://nuphy.com/pages/firmware).
- The NuPhyIO landing page lists Air75 V3 ANSI, ISO, and JIS as supported
  devices: [NuPhyIO device list](https://www.nuphy.io/en-US).
- The official landing-page client launches the web application at
  `https://drive.nuphy.io/`. The application artifact inspected for this check
  was [main.f6f60294.js](https://drive.nuphy.io/static/js/main.f6f60294.js).
  Its HTTP metadata reported `Last-Modified: Mon, 15 Jun 2026 07:44:24 GMT`;
  the SHA-256 of the decompressed artifact was
  `3e90833c5db2cc1cbe8e0243ec32b0528c1d2d62cef17dabb358bc728b27695b`.

The application artifact explicitly models decimal VID/PID `6645:9760`, which
is hexadecimal `19f5:2620`, as its `U1` dongle. It separately models Air75 V3
and assigns that keyboard `dongleType: "U1"` with an Air75 V3 virtual data
file. This is first-party evidence that the current NuPhyIO client is designed
to reach Air75 V3 through this proprietary NuPhy dongle. It is not evidence
that the dongle is Logi Bolt; it is not.

## Live official-client experiments

### NuPhy 2.4 GHz dongle

The production NuPhyIO catalog returned by
`/prod-api/api/nuphyIo/dongleList` lists `19f5:2620` as `NuPhy U1 Dongle`, and
the Air75 V3 catalog entry links to that dongle. However, NuPhyIO's actual
`navigator.hid.requestDevice()` filter omitted PID `2620`. Its normal chooser
therefore reported no compatible device.

A temporary in-page change appended only the catalog's exact U1 filter
(`19f5:2620`, usage page `1`, usage `0`). Brave then returned exactly one U1
device to NuPhyIO. NuPhyIO called `HIDDevice.open()`, but the open failed with
`NotAllowedError` before any HID traffic:

- zero output reports were sent;
- zero input reports were received;
- `window.keyboardApi` was not created.

This confirms that WebHID chooser authorization succeeded. The preserved trace
does not distinguish whether the subsequent `NotAllowedError` came from OS
hidraw access or NuPhyIO's device-opening path. In either case, the current
official application produced no U1 request/response transaction to analyze.

### Wired Air75 V3

The repository's earlier Ubuntu recovery guide,
`private_dot_config/nuphy/NuPhy Keyboard Firmware Update on Linux.md`, records
that successful NuPhyIO firmware access used a data-capable USB cable and wired
mode. Its broad `chmod`/`0666` permission suggestions were not reused.

With the dongle left plugged in and the keyboard's selector still in its
wireless position, connecting the USB cable exposed `19f5:1028` (`Air75 V3`).
Its interface `03` had the same 64-byte input/output descriptor and the same
descriptor SHA-256 as dongle interface `03`. Official NuPhyIO opened the wired
interface successfully and completed initialization.

The captured wired trace contained 475 events:

- 141 64-byte output reports, all beginning with `0x55`;
- 141 corresponding 64-byte input reports beginning with `0xaa`;
- 22 unsolicited diagnostic input reports beginning with `0xfe`;
- no `getBatteryState` call and no trace entry labelled
  `BatteryStateReport`; the capture did not instrument API event emission.

The official client artifact and trace establish the general framing:

- request flag byte `0` is `0x55`; response flag byte `0` is `0xaa`;
- byte `1` is the command/opcode and was echoed by all 141 matched responses;
- byte `2` is the command key and was also echoed by all 141 responses;
- byte `3` is an 8-bit checksum: the sum of bytes `4..63`, modulo 256;
- bytes `4..7` encode length, 16-bit address, and handle;
- after the session-key handshake, bytes `4..7` and data bytes are XORed with
  a per-session secret generated by NuPhyIO.

All 141 request/response pairs were 64 bytes. Response latency ranged from
approximately 1.6 ms to 42.8 ms (mean 2.66 ms). The session-key handshake means
captured encrypted packet bytes are not a portable command template.

The mode-`0600` raw capture was saved temporarily as
`/tmp/nuphyio-wired-trace.json`, SHA-256
`22b945ccc975770c205d8ab3550d52501dcacae63de2274ebf0659d891808d5c`.
The temporary ACLs on both the dongle and wired interface were removed. Each
node was dynamically re-resolved by VID/PID, interface `03`, and the report
descriptor fingerprint; both then showed only the original owner entry and no
extended user ACL. After unplugging the cable, final sysfs inspection showed
`19f5:2620` present and `19f5:1028` absent; the selector had remained in its
wireless position throughout.

## Battery result

The official client contains a generic battery component and a
`getBatteryState`/`BatteryStateReport` path. However, the predicate that enables
the battery display (`isSupportBatteryShow`) checks a support set containing
only `WH80` and `WH80ByDongle`. Air75 V3, Air75 V3 ISO, and Air75 V3 JIS are in
a different device-family set and are not members of the battery-display set.

The live wired object confirmed the static finding:

- `window.keyboardApi` existed, but `getBatteryState` was absent from the
  instance and every prototype level;
- a passive scan of 847 already-loaded objects found no cached
  battery/charge/power value;
- the only battery-named objects were empty generic `BatteryStateReport`
  listener sets;
- a passive scan of 1,523 loaded function objects found no Air75 V3 battery
  parser or query method, only the generic event-listener constructor.

Therefore the current official NuPhyIO build does **not** provide a known-good
numeric Air75 V3 battery display to correlate with a 2.4 GHz request/response.
The mere presence of generic battery code is not enough to identify an Air75
V3 battery command. Even if a lower layer makes an unsupported or hidden
status call, it would not provide a displayed value against which to validate
an opcode, response byte, precision, checksum, or offline behavior.

## Live Linux reconfirmation

- USB `19f5:2620` exposes four HID interfaces (`00` through `03`).
- Interface `03` has the 64-byte input and 64-byte output report descriptor.
  Its descriptor SHA-256 is
  `bfae8e2dc548276f9fcabf14b0d22832b738d369daf59c4e916b6bc7929a9b25`.
- The four hidraw nodes were initially `0600 root:root`, with no extended user
  ACL. Approved ACLs were limited to interface `03`; no persistent rule was
  installed.
- UPower enumerated only the laptop battery, AC/USB line-power devices, and
  the display device. Sysfs exposed no NuPhy power-supply or battery node.

The interface number and descriptor fingerprint are stable identification
evidence; the observed `/dev/hidrawN` number is not a stable identifier and
must not be used by an implementation.

## Blocker and remaining unknowns

There is no official Air75 V3 battery value and hence no known-good battery
transaction to capture. The live wired trace demonstrates protocol traffic but
contains no battery method or event with which to label one of its 141 commands.
Replaying one of those commands on the dongle would therefore be a guess and
would not satisfy even the relaxed requirement that the request originate from
an identifiable official battery API. The 2.4 GHz path stops without a helper,
udev rule, or Waybar module.

Still unknown:

- whether a future NuPhyIO build will enable Air75 V3 battery display;
- whether the Air75 V3 firmware exposes battery state internally through the
  U1 dongle despite the UI not supporting it;
- the battery request opcode and fields, response field, precision, and
  asleep/offline behavior for any such internal state.

Bluetooth/UPower remains a separate optional fallback only if explicitly
approved; it was not tested or enabled during this check.
